## Technical Background: What Are LoRA Adapters?

### What We Fine-Tuned

We fine-tuned **LoRA adapters** on top of the base **TinyLlama-1.1B-Chat-v1.0** model. We created two separate adapters:

1. **orchestrator_adapter_v2** - Routes between COMMAND and CHAT modes, extracts intents and parameters
2. **persona_adapter** - Handles conversational responses with Tomo's personality

### What is LoRA?

**LoRA = Low-Rank Adaptation**

LoRA is a parameter-efficient fine-tuning technique that:

- **Does NOT modify the base model weights** - The original TinyLlama 1.1B stays frozen and unchanged
- **Adds small "adapter" layers** - These are lightweight matrices that sit alongside the original weights
- **Only trains ~0.1-1% of parameters** - Instead of billions of parameters, you train millions

#### How it works:
```
Original weight matrix: W (frozen)
LoRA adds: ΔW = B × A (trainable)
Final output: W + ΔW
```

Where B and A are small low-rank matrices that are much cheaper to train and store.

### What Did We Actually Change?

When we ran the fine-tuning process:

✅ **Created new adapter weights** - Small files containing the LoRA parameters
✅ **Trained these adapters** - Updated only the adapter weights, not base model
✅ **Saved to disk** - Stored as separate adapter files that can be loaded on demand

❌ **Did NOT change** - The base TinyLlama 1.1B model weights remain completely untouched

### Why This Matters for Tomo

1. **Efficiency** - You can switch between different adapters quickly (orchestrator vs persona)
2. **Multiple personalities** - Could train different persona adapters without retraining everything
3. **Small storage** - Adapters are ~10-100MB vs multi-GB for full models
4. **Base model quality** - Still benefit from Google's original training
5. **Experimentation** - Can try different adapter versions without risk

**Important:** The 76.7% success rate in these results reflects the quality of the **adapter weights** we trained, not changes to the underlying model.

## Key Findings

### Strengths
1. **Strong Intent Recognition (90% success rate):** The orchestrator correctly identifies user intent in most cases
2. **Good Data Extraction:** When intent is correct, parameter extraction is generally accurate
3. **Appropriate Chat Routing:** Most conversational queries are correctly routed to persona adapter
4. **Multi-parameter Handling:** Can extract multiple structured fields (recipient, time, target, action, etc.)
5. **Flexible Schema:** Uses appropriate key names for different contexts

### Critical Issues

#### 1. Query vs. Command Confusion (Test 10)
- **Problem:** "Is 'finish the report' on my to-do list?" → misinterpreted as `add_to_list`
- **Impact:** High - users asking questions get unwanted actions
- **Fix:** Add training examples distinguishing questions from commands:
  - "Is X on my list?" → `check_list`
  - "Add X to my list" → `add_to_list`

#### 2. Model Escalation Not Understood (Tests 23, 25)
- **Problem:** Requests to use "more powerful model" or "ask a larger model" not recognized
- **Impact:** High - critical for multi-stage processing use case
- **Fix:** Add training examples for:
  - "I need a more powerful model for..." → `forward_to_home_llm`
  - "Ask a larger model to..." → `forward_to_home_llm`
  - "Phone home and ask Claude..." → `forward_to_home_llm`

#### 3. Incomplete Parameter Extraction (Test 12)
- **Problem:** Failed to extract recipient field for text message
- **Impact:** Medium - functional but requires extra parsing
- **Fix:** Improve training examples to emphasize recipient extraction:
  - "Text [PERSON] and say [MESSAGE]" → `{'recipient': 'PERSON', 'message': 'MESSAGE'}`

#### 4. Opinion Questions Routed to Commands (Test 30)
- **Problem:** "What do you think about..." → `forward_to_home_llm` instead of chat
- **Impact:** Low-Medium - might work but not ideal UX
- **Fix:** Add examples routing opinion/philosophical questions to chat mode
